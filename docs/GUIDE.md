# Дебюрократизатор — подробное описание проекта

Этот документ объясняет **как запустить проект через Docker**, **как им пользоваться**
и **как всё устроено внутри** — простым языком, но с точными ссылками на файлы.
После прочтения вы сможете ответить на вопросы вида «где применяется эмбеддинг»,
«какой промпт у критика», «как работает HITL».

---

## Часть 1. Запуск через Docker

### 1.1. Что нужно заранее

- **Docker Desktop** (Windows/Mac) или Docker Engine (Linux) — с включённым Docker Compose v2.
- ~12 ГБ свободного места: образы (~4 ГБ) + модель Ollama `qwen2.5:7b` (~4.7 ГБ) + Python-зависимости в образе.
- Больше ничего: ни Python, ни Ollama на хосте не нужны — всё живёт в контейнерах.

### 1.2. Запуск (одна команда)

```bash
cd debureaucratizer
cp .env.example .env
docker compose -f infrastructure/docker-compose.yml up -d
```

Первый запуск долгий (10–30 минут): собирается образ приложения и скачивается
LLM-модель. Дальнейшие запуски — секунды.

Что поднимается (9 сервисов):

| Сервис | Что это | Порт |
|---|---|---|
| `db` | Postgres 16 — пользователи, глоссарий, TM, кэш, HITL-очередь | внутренний |
| `redis` | Брокер сообщений для Celery | внутренний |
| `qdrant` | Векторная БД (поиск по эмбеддингам) | 6333 |
| `ollama` | LLM-сервер | 11434 |
| `ollama-pull` | Одноразовая задача: скачивает модель в общий том и завершается | — |
| `app` | FastAPI-бэкенд | 8000 |
| `worker` | Celery-воркер (фоновые задачи) | — |
| `ui` | Streamlit-интерфейс | 8501 |
| `nginx` | Reverse proxy перед API | 80 |

### 1.3. Первичная загрузка данных

База создаётся пустой. Эталонные данные (глоссарий 650 пар, TM 5876 пар)
загружаются один раз:

```bash
DC="docker compose -f infrastructure/docker-compose.yml"

$DC exec app python scripts/import/add_glossary.py --builtin
$DC exec app python scripts/import/add_tm.py --builtin
$DC exec app python scripts/import/create_admin.py admin@example.com --password 'Secret123'
$DC restart app    # чтобы TM попала в поисковые индексы (BM25 + Qdrant)
```

### 1.4. Как пользоваться

1. Откройте **http://localhost:8501** — это интерфейс.
2. Зарегистрируйтесь (вкладка «Регистрация») или войдите как админ
   (`admin@example.com` / пароль из шага 1.3).
3. Страница **«Перевод»**: вставьте канцелярский текст, нажмите «Упростить».
   Первый запрос может занять 1–2 минуты (модель загружается в память),
   дальше — секунды. Под результатом видны оценка критика и журнал агентов.
4. Остальные страницы:
   - **Мульти и батч** — один текст в несколько стилей / пачка текстов сразу;
   - **Ensemble** — несколько моделей отвечают, критик выбирает лучший вариант;
   - **Глоссарий**, **Память переводов** — справочники (только admin);
   - **Оценка качества** — BLEU / chrF++ / BERTScore по своим парам текстов;
   - **HITL** — очередь спорных переводов на ручную проверку (admin/editor);
   - **Админ** — статус сервисов и статистика кэша.

API доступен и напрямую: Swagger UI — **http://localhost:8000/docs**,
через nginx — http://localhost/health.

### 1.5. Полезные команды

```bash
DC="docker compose -f infrastructure/docker-compose.yml"

$DC ps                  # статус сервисов (healthy?)
$DC logs -f app         # логи бэкенда
$DC logs -f worker      # логи фоновых задач
$DC down                # остановить всё (данные сохранятся в томах)
$DC down -v             # остановить и УДАЛИТЬ все данные (БД, модель!)
$DC up -d --build app   # пересобрать приложение после изменения кода
```

### 1.6. Типичные проблемы

- **`ollama-pull` упал с TLS timeout** — сеть/прокси мешает скачать модель.
  Просто повторите: `docker compose -f infrastructure/docker-compose.yml up ollama-pull`.
- **Перевод возвращается с движком `huggingface`** — Ollama недоступна или модель
  не скачана. Проверьте `$DC logs ollama-pull` и `curl http://localhost:11434/api/tags`.
- **Порт 80 занят** — поменяйте в compose `"80:80"` на `"8080:80"`.
- **Забыли пароль админа** — создайте нового: `$DC exec app python scripts/import/create_admin.py new@admin.com`.

## Часть 3. Жизненный цикл одного запроса на упрощение

Что происходит, когда вы нажимаете «Упростить» (код — `backend/services/pipeline.py`,
функция `perform_translation`):

1. **Проверка кэша.** Если текст уже упрощался в том же режиме и движке — ответ
   отдаётся мгновенно из таблицы `translation_cache` (`backend/data/cache.py`).
   Кэшируются только успешные результаты домена `general`.
2. **Глоссарий.** Из таблицы `glossaries` выбираются канцеляризмы, которые
   встречаются в вашем тексте (`glossary_store.find_relevant` — просто поиск
   подстроки по справочнику, с in-memory кэшем справочника).
3. **Поиск примеров (RAG).** По памяти переводов (TM, таблица
   `translation_memories`) ищутся до 5 похожих пар «сложное → простое»
   (подробности в части 5).
4. **Сборка промпта.** `build_prompt` складывает: системную инструкцию,
   список подходящих замен из глоссария (до 20), найденные примеры (до 5,
   с их скорами) и сам текст.
5. **Вызов LLM.** `translator_manager.translate` решает, какой движок использовать
   (Ollama или HuggingFace — часть 6), генерирует черновое упрощение, ответ
   чистится от служебного мусора (`clean_translation`).
6. **Мультиагентный контур.** Черновик проходит цепочку
   Validator → Critic → (Editor → повторная проверка)* под управлением
   Supervisor (часть 4 — самая важная).
7. **Постобработка.** Если итог неуспешен — он попадает в HITL-очередь на
   разбор человеком. Если успешен — пишется в кэш. Ответ уходит в API/UI
   вместе с `reasoning_log` (журналом решений агентов).

Весь этот сценарий параметризован **режимом** (`eval_mode`): можно отключать
глоссарий, TM, критика, редактора — всего 8 комбинаций для измерения вклада
каждого компонента (часть 9).

## Часть 4. Мультиагентная система

Фреймворки не используются: всё написано вручную. Общий интерфейс агента —
`BaseAgent.process(state)` (`backend/agents/base.py`): каждый агент получает
общий словарь состояния, дописывает в него свои поля и возвращает обратно.
LLM-вызовы идут через `Agent._call_llm` — единая точка с retry (3 попытки)
и фиксированным `seed=42` (воспроизводимость ответов).

### 4.1. Validator — проверка без LLM (`backend/agents/validator.py`)

Чисто алгоритмические проверки (быстрые, бесплатные):

- **Ошибки** (блокируют): пустой ответ; «эхо» (результат совпадает со входом);
  несовпадение плейсхолдеров `%s`/`%1$s`; в тексте < 50% кириллицы; CJK-иероглифы.
- **Предупреждения**: оставшиеся канцеляризмы (словарь `BUREAUCRATIC_MARKERS` —
  «надлежащим образом», «во исполнение» и т.п.); повторы слов подряд;
  дословные фрагменты источника от 4 «тяжёлых» слов подряд (независимо от регистра);
  пропавший термин глоссария.

Про глоссарий подробнее: если канцеляризм из глоссария был во входе, валидатор
ждёт в выходе его простой эквивалент. Сначала ищет точное совпадение, а если нет —
**семантическую проверку эмбеддингом**: считает косинусную близость векторов
«эквивалент» ↔ «весь результат», и при сходстве ≥ 0.7 засчитывает присутствие
(так «оплатить» засчитывается за «заплатить»). Это одно из двух мест,
где применяются эмбеддинги.

### 4.2. Critic — оценщик качества (`backend/agents/critic.py`)

LLM-as-a-Judge: просит модель оценить упрощение по шкале 0–10.

**Промпт** (метод `_build_prompt`): роль «строгий эксперт-оценщик»,
4 few-shot примера (хорошее упрощение / потерян смысл / остался канцелярит /
эхо источника), для доменов `legal` и `gov` — дополнительный пример
(«нельзя менять суммы, сроки, статьи»), затем жёсткие правила:

- `adequacy` — сохранён ли смысл и факты (изменённая дата/сумма/имя → 0);
- `fluency` — естественность (канцеляризмы или грамматические ошибки → ≤ 5);
- `terminology` — сохранены ли обязательные термины;
- `overall_score` + конкретные `suggestions`;
- формат ответа — строго JSON.

Ответ разбирается сканером `_extract_json_spans` (вырезает JSON-объекты
балансировкой скобок — модель любит обрамлять JSON текстом), с запасной
regex-вытаскивалкой `overall_score`. Не распарсилось или LLM недоступна —
`critic_failed=True`, и Supervisor останавливает цикл (без оценки улучшать
некорректно).

### 4.3. Editor — исправляет по замечаниям (`backend/agents/editor.py`)

Запускается, только когда есть что чинить: ошибки/предупреждения валидатора
или suggestions критика. Пропускается при `critic_failed` и при «no issues».

**Промпт** (`_build_prompt`): роль «редактор», исходный канцелярский текст,
текущее упрощение, нумерованный список замечаний («ОШИБКА: …»,
«ПРЕДУПРЕЖДЕНИЕ: …», «ПРЕДЛОЖЕНИЕ: …») и жёсткие правила:
применять замечания буквально, не добавлять факты, даты/суммы/имена не трогать,
«NO-CHANGE лучше, чем сломанное изменение», вернуть только текст.

Пустой ответ или недоступность LLM → `editor_failed=True`, оригинал сохраняется.

### 4.4. Supervisor — дирижёр (`backend/agents/supervisor.py`)

Управляет циклом и принимает решения:

1. Прогоняет Validator и Critic над черновиком.
2. **Адаптивный бюджет итераций** по оценке критика (`_adaptive_budget`):
   score < 4.0 → 3 итерации; 4.0–7.0 → 2; ≥ 7.0, но есть замечания → 1;
   ≥ 7.0 без замечаний → 0 (сразу готово). Пороги — `backend/core/constants.py`.
3. На каждой итерации: **snapshot** состояния → Editor правит → повторные
   Validator + Critic → сверка:
   - стало хуже (score упал или валидация сломалась) → **rollback**: состояние
     откатывается к снимку, стоп (`rollback_regression`);
   - редактор ничего не изменил → стоп (`no_change`);
   - валидация пройдена и score ≥ 7.0 и замечаний нет → **converged**, успех;
   - бюджет исчерпан → `max_iterations`.
4. Ошибки агентов тоже обрабатываются: `critic_failed` / `rollback_error`.
5. Всё пишется в **`reasoning_log`** — список шагов «кто что решил» с оценками.
   Его показывает UI (expander'ы на странице «Перевод») — это объяснимость системы.

Поле `final_success` — итоговый вердикт: валидация пройдена и (критик выключен
или score ≥ 7.0). От него зависят кэширование и HITL.

## Часть 5. RAG: как устроен поиск примеров

Цель: дать LLM в промпт похожие примеры «как надо упрощать».

### 5.1. Два источника данных

- **Глоссарий** (`glossaries`, 650 записей): короткие пары «канцеляризм →
  простой эквивалент» («осуществление» → «выполнение»). Попадает в промпт
  списком замен.
- **Память переводов / TM** (`translation_memories`, 5876 пар): целые
  предложения «сложное → простое». По ним строится поиск.

Оба набора — синтетические (`scripts/import/builtin_data.py`: шаблоны +
комбинаторика, помечено в README как синтетика — это допустимо по заданию).

### 5.2. Лексический поиск — BM25 (`backend/retrieval/bm25_index.py`)

Классический алгоритм из информационного поиска: документы — это source-части
TM-пар, запрос — ваш текст; учитывает частоту слов и длину документов.
Реализация — библиотека `rank_bm25`, индекс лениво перестраивается при записи.
Сильная сторона: точные совпадения терминов. Слабая: синонимы не находит.

### 5.3. Векторный поиск — эмбеддинги + Qdrant (`backend/retrieval/vector_index.py`, `backend/data/embeddings.py`)

**Эмбеддинг** — это вектор чисел (384 измерения), в который модель
`paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers) упаковывает
смысл текста. Тексты с близким смыслом получают близкие векторы, даже если
слова разные.

Где применяется в проекте (два места):
1. **Здесь, в RAG**: source-части всех TM-пар заранее превращены в векторы
   и лежат в Qdrant (коллекция `tm_entries`, метрика cosine). При запросе ваш
   текст тоже векторизуется, и Qdrant возвращает ближайшие пары. Находит
   примеры «по смыслу», а не по буквам.
2. **В валидаторе** (часть 4.1): семантическая проверка «появился ли простой
   эквивалент термина в результате».

Модель эмбеддингов — синглтон (`EmbeddingModel`), грузится один раз на процесс.

### 5.4. Слияние — RRF (`backend/retrieval/hybrid_retriever.py`)

Оба поиска возвращают свои списки. **Reciprocal Rank Fusion** складывает их
по формуле `score = Σ 1/(60 + rank + 1)` — позиция в выдаче важнее «сырых»
скоров, дубликаты сливаются и всплывают наверх. Итог — устойчивый топ-5,
который и идёт в промпт с пометками score.

### 5.5. Когда индексы обновляются

При старте API (`ensure_indexes_loaded` в `pipeline_state.py`) TM из БД
загружается в BM25 и дозаписывается в Qdrant. Полная переиндексация
(пересоздание коллекции) — только фоновой задачей Celery
`index_translation_memory`: она запускается автоматически после массового
импорта TM и после подтверждения правок в HITL.

## Часть 6. Движки LLM (`backend/data/translator_manager.py`)

- **Ollama** — основная: локальная модель `qwen2.5:7b`, HTTP API
  (`backend/utils/llm_client.py`). Все вызовы с `seed=42` — повторяемые ответы.
- **HuggingFace Transformers** — запасная (`facebook/nllb-200-distilled-600M`),
  на случай недоступной Ollama. Честно помечена в README: это межъязыковой
  переводчик, для переноса стиля подходит слабо — аварийный вариант.

`TranslatorManager.choose_engine` решает, куда идти: раз в 30 секунд пробует
`/api/tags` Ollama (TTL-кэш пробы), проверяет, что стилевая пара известна.
Если просили `ollama`, а он недоступен — фолбэк на HF (если
`FALLBACK_TO_HF_ON_ERROR=true`). Для честной оценки есть `strict_engine=True`:
фолбэк превращается в ошибку `EngineFallbackTriggeredError` — чтобы
eval-режимы незаметно не деградировали в baseline.

Ответ любой LLM пропускается через `clean_translation`
(`backend/utils/llm_processing.py`): срезает префиксы («Перевод:»), JSON-обёртки,
markdown-ограждения, английские мета-фразы, китайскую пунктуацию от Qwen.

## Часть 7. Кэш (`backend/data/cache.py`, таблица `translation_cache`)

Ключ: `(source_lang, target_lang, engine, eval_mode, model, source_text)`.
Пустые поля хранятся как сентинел `"unknown"` (NULL в UNIQUE-индексах
ненадёжен). На чтении `None` = «любое значение». При хите растёт счётчик
`hits` (виден на странице «Админ»). Пишется **только успешный** результат
и только для домена `general` (настраивается `CACHEABLE_DOMAIN`).
Очистка — админ-роут или периодическая задача `clear_old_cache(days=30)`.

## Часть 8. HITL — человек в контуре (`backend/hitl/`)

Human-in-the-Loop работает так:

1. **Пополнение очереди.** Каждый раз, когда пайплайн завершился с
   `final_success=False` (критик дал < 7, или валидация не пройдена, или
   критик не сработал), пример автоматически падает в таблицу
   `uncertain_examples` со статусом `pending` (`push_uncertain`).
2. **Разбор человеком.** Редактор/admin открывает страницу «HITL» в UI
   (или роуты `/hitl/uncertain`): видит исходник, машинный вариант, оценку.
   Дальше два пути:
   - **confirm** — принять как есть или вписать свою правку. Пара
     «исходник → принятый вариант» **автоматически пополняет TM**
     (`active_learning.confirm` → `tm_store.insert_in_session`), а задача
     Celery переиндексирует поиск. Система учится на разобранных ошибках.
   - **reject** — отклонить; в TM не попадает.
3. **Ручные корректировки.** Можно и вне очереди: `/hitl/save-correction`
   (страница HITL) сразу кладёт пару в TM (`feedback.save_correction`).

Так замыкается цикл active learning: худшие случаи → человек → база знаний →
лучшие промпты в будущем.

## Часть 9. Оценка качества: режимы и метрики

**8 режимов** (таблица в README, код — `EVAL_MODES` в `pipeline.py`):
от `baseline` (голая LLM) до `full` (всё включено). Режим отключает/включает
глоссарий, TM (BM25 или гибрид), критика, редактора. Зачем: измерить вклад
каждого компонента отдельно (ablation study — требование задания).

**Прогон**: `scripts/eval/prepare_eval_datasets.py` готовит датасеты размеров
10–1000 (`data/eval/bureau-plain_*.json`, уже сгенерированы), затем
`scripts/eval/run_eval.py data/eval/bureau-plain_10.json` гоняет каждый режим
с `strict_engine=True` и считает метрики (`backend/eval/`):

- **BLEU** и **chrF++** (sacrebleu) — классика машинного перевода: совпадение
  n-грамм / символьных n-грамм с эталоном;
- **BERTScore** — близость по эмбеддингам (ещё одно место, где векторы);
- **METEOR** — учитывает синонимы и порядок слов.

Те же метрики доступны в UI на странице «Оценка качества» и через роут `/eval`.

## Часть 10. Фоновые задачи Celery (`backend/worker/`)

| Задача | Зачем |
|---|---|
| `index_translation_memory` | Полная переиндексация TM → BM25 + пересоздание коллекции Qdrant |
| `batch_translate` | Пачка переводов в фоне (семафор 4 — не душим LLM) |
| `run_evaluation_async` | Метрики в фоне |
| `clear_old_cache` | Чистка кэша старше N дней (по расписанию beat) |
| `add_glossary_bulk` / `add_tm_bulk` | Массовый импорт; TM-импорт сам запускает переиндексацию |

Важная техническая деталь: у воркера **один event loop на процесс**
(`get_worker_loop` в `celery_app.py`), а не новый loop на задачу — иначе
SQLAlchemy падает с «attached to a different loop».

## Часть 11. Аутентификация и роли

- Регистрация/вход — `/auth/register`, `/auth/login` (`backend/api/routes/auth.py`).
  Пароль: ≥ 8 символов, цифра, заглавная; хранится bcrypt-хэш
  (`backend/utils/security.py`).
- Дальше — JWT (HS256, срок `JWT_EXPIRATION_MINUTES`) в заголовке
  `Authorization: Bearer ...`.
- Роли: `user` (переводит), `editor` (+ HITL), `admin` (+ справочники, кэш).
  Проверки — `require_admin` / `require_editor` в `backend/api/deps.py`.
  Первым админом становитесь через `scripts/import/create_admin.py`.

## Часть 12. Шпаргалка «вопрос → ответ»

**Где применяется эмбеддинг?**
Два места: (1) векторный поиск примеров в RAG — TM-пары лежат в Qdrant как
векторы модели `paraphrase-multilingual-MiniLM-L12-v2` (`backend/retrieval/vector_index.py`);
(2) семантическая проверка глоссария в валидаторе — если точной строки нет,
считается косинусная близость ≥ 0.7 (`backend/agents/validator.py:_semantic_match`).
Плюс третье, косвенное: метрика BERTScore.

**Какой промпт использует каждый агент?**
- LLM-переводчик: `build_prompt` в `backend/services/pipeline.py` — инструкция
  + замены из глоссария + до 5 примеров из TM со скорами + сам текст.
- Critic: `_build_prompt` в `backend/agents/critic.py` — 4 few-shot примера,
  доменный пример для legal/gov, правила adequacy/fluency/terminology,
  ответ строго в JSON.
- Editor: `_build_prompt` в `backend/agents/editor.py` — исходник, текущий
  вариант, список замечаний и правило «NO-CHANGE лучше сломанного изменения».
- Validator и Supervisor — без промптов, это чистая логика.

**Как работает HITL?**
Неуспешный результат пайплайна сам падает в очередь `uncertain_examples` →
человек на странице «HITL» подтверждает (с правкой или без) или отклоняет →
подтверждённая пара дописывается в TM → Celery переиндексирует поиск →
следующие переводы получают лучший few-shot контекст.

**Почему поиск гибридный (BM25 + векторы)?**
BM25 находит точные термины, но слеп к синонимам; векторы находят смысл, но
могут упустить точную формулировку. RRF (k=60) усредняет по рангам — оба
сигнала дополняют друг друга, дубликаты всплывают.

**Как обеспечена воспроизводимость?**
`seed=42` на всех вызовах Ollama (`DEFAULT_SEED`), `temperature=0` у критика,
детерминированные id записей (sha256), фиксированный seed в eval-датасетах.

**Как тесты изолируют внешние сервисы?**
БД — in-memory SQLite (фикстура `test_db`); Ollama, Qdrant, эмбеддинги,
Celery-брокер — моки/monkeypatch. Поэтому 140 тестов проходят без единого
живого сервиса за ~1 минуту, покрытие 86%.

**Почему кэш только для домена general?**
Правовые/медицинские тексты чувствительны к контексту: безопасно кэшировать
только «бытовой» домен, где повторный ответ на тот же вход точно уместен
(константа `CACHEABLE_DOMAIN`).
